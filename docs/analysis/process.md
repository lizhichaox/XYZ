## 0. Summary (read this first)

1. **The build configuration itself is "hand-written pbxproj + xcconfig as the single version source", and the version claim is real**: the bundled products (Debug / Release / iOS Simulator) all report `0.5.28 (44)` in `Info.plist` when measured, `project.pbxproj` contains no `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` / `DEVELOPMENT_TEAM` override (`grep` is empty), and the locally installed `/Applications/XYZ.app` measures `0.5.27 (43)`, matching CHANGELOG line 5 and docs/architecture.md line 3.
2. **But the whole "release" loop does not exist**: no tags, no release workflow, no archive/notarization/Developer ID signing; Release still sets `ENABLE_HARDENED_RUNTIME = NO`; HEAD itself is red on its own CI acceptance gate (run 42332912178), and the single version number 0.5.28/44 is shared by 18 commits, while the "rollback" commit `02dac3c` named in the docs predates the fixes recorded for 0.5.28.
3. **CI's "pass" validates a different binary from the one users run**: CI builds with `CODE_SIGNING_ALLOWED=NO` and then re-signs ad hoc with `codesign --force --deep --sign -`; a comparable local build product measures **empty** entitlements under `codesign -d --entitlements -`, so CI runs an app with **no sandbox, no iCloud, no bookmarks**, whereas the installed 0.5.27 is a development-signed bundle carrying App Sandbox/iCloud entitlements. The sandbox, iCloud sync and bookmark paths never pass through CI at all.
4. **UI acceptance is an in-process self-check (2,459 lines of `GutterSnapshot.swift` shipped in the release bundle) plus window-screenshot OCR**: it depends on WindowServer/TCC/Vision and the deprecated `CGWindowListCreateImage`, has a hard 90-second timeout, and 5 acceptance cases are known to fail with no code change after `da9730d` (CI history 137/380 successes, only 10 successes in the last 100 runs — the gate is both slow and red). It cannot prove the product is correct; it only proves that the checker itself did not report an error.
5. **The bilingual promise is only half kept**: `Localizable.xcstrings` has 234 keys / 232 zh-Hans entries (the coverage looks high), but after comparing literals in the code, **at least 47 user-visible strings are not in the catalog** (menus, tab context menu, search panel, status bar, settings), so the Chinese UI falls back to English; the catalog simultaneously retains keys for removed features (Format menu, sidebar filter, and so on). CI's Chinese check greps exactly one string, "Open Folder…".
6. **The CLI `xyz` has documented but non-working functionality**: `xyz ~` / `xyz ~/Notes` can never match the `~)` branch because POSIX `case` patterns undergo tilde expansion, and the measured result is `No such file or directory`; the CLI's own `--help` line 30 and README line 28 both advertise this usage, and `Scripts/xyz-test.sh` does not cover it.
7. **Repository hygiene is generally good** (clean tree, no build/.build committed, `.gitignore` coverage, repo only 1.5 MB, every plist lints OK), but there is no lint/format gate, no app test target, no caching or timeout, and no branch or tag policy; 154 commits are compressed into 2 days (153 of them on 11-02~11-03), and the messages read like an AI agent iteration log (5 Cursor Agent commits, 10 carrying `Co-Authored-By: Claude 5.5`).

## 1. Build / signing configuration

### 1.1 The pbxproj is hand-written, not generated by Xcode or xcodegen

**Conclusion**: `XYZ.xcodeproj/project.pbxproj` (560 lines) is a project file **maintained by hand / generated once by an ad-hoc script and then maintained by hand**; it is neither a normal Xcode GUI product nor an xcodegen product.

Evidence:

- There is no `project.yml` in the repository (`ls project.yml` finds nothing; there is no yml at the root at all); xcodegen 2.46.0 is installed locally but unused; the pbxproj carries no `XcodeGen` / `DO NOT EDIT` / `generated` marker.
- The UUIDs are synthetic numbering rather than Xcode's random 24-character hex: the `8A0000000000000000000001`, `8B…0001`, `8C…0001` scheme (`project.pbxproj:10`, `:46`, `:235`, `:545`); the file has 95 unique 24-hex IDs in total, all following the sequential `8[ABC]0…` pattern. Xcode normally writes random hex (such as `A1B2C3D4…`) and includes metadata such as `LastSwiftMigration`/`LastSwiftUpdateCheck`.
- The format is old: `objectVersion = 56` (`project.pbxproj:6`), `compatibilityVersion = "Xcode 14.0"` (`:248`), `LastUpgradeCheck = 2600` (`:239`), `CreatedOnToolsVersion = 26.0` (`:243`).
- File references are registered entirely by hand: 39 `PBXFileReference` entries and 27 source-file references; comparing the on-disk `XYZ/**.swift` files with the pbxproj references by script gives **27/27 one-to-one, nothing missing and nothing extra** (the current state is correct). The `bin` resource is a folder reference (`:77`, `:278`).

**Impact**: adding or renaming a source file requires editing the pbxproj text by hand; a missed registration raises no error and simply produces "the file exists but is not compiled" — the most typical silent failure of a hand-written pbxproj. The current tree happens to be consistent, but nothing guarantees future consistency.

**Recommendation**: introduce `project.yml` + xcodegen (already installed, 2.46.0) to generate the pbxproj; or add a 10-line CI script that diffs `xcodebuild -list` or the parsed pbxproj against the on-disk file list and fails when they disagree.

### 1.2 xcconfig as the single version source: the claim holds, with one implicit dependency

**Conclusion**: `MARKETING_VERSION = 0.5.28` and `CURRENT_PROJECT_VERSION = 44` in `Config/Base.xcconfig:6-7` really are the **only version source**; the pbxproj does not override them (`grep -n "MARKETING_VERSION\|CURRENT_PROJECT_VERSION\|DEVELOPMENT_TEAM" project.pbxproj` returns nothing), and both target configurations attach a `baseConfigurationReference` (`project.pbxproj:433` Debug, `:478` Release).

Measured verification (the Lead's build products, local `build/`):

- macOS Debug `XYZ.app/Contents/Info.plist`: `CFBundleShortVersionString = 0.5.28`, `CFBundleVersion = 44`;
- macOS Release: likewise 0.5.28 / 44;
- iOS Simulator Debug: likewise 0.5.28 / 44;
- the About window reads `Bundle.main` (`XYZ/Workspace/EditorCommands.swift:1288-1289`), so the version shown in About also comes from this generated plist.

**Implicit dependency**: the two hand-written plists **do not contain** version keys themselves (neither `XYZ/Info.plist` nor `XYZ/Info-macOS.plist` has `CFBundleShortVersionString`/`CFBundleVersion`); the version appears only because `GENERATE_INFOPLIST_FILE = YES` (`project.pbxproj:444`, `:489`) merges `$(MARKETING_VERSION)`/`$(CURRENT_PROJECT_VERSION)` into the specified plist (the macOS product measurably contains both the hand-written key `NSUbiquitousContainers` and the generated key `LSMinimumSystemVersion=14.0`). The moment someone turns `GENERATE_INFOPLIST_FILE` off, the version silently disappears.

**Recommendation**: add a one-line CI assertion (`plutil -extract CFBundleShortVersionString` must equal the value in `Config/Base.xcconfig`), turning "single source" into an executable contract.

### 1.3 Empty DEVELOPMENT_TEAM + signing disabled in CI: the CI product is not the app users run

**Conclusion**: `DEVELOPMENT_TEAM =` on `Config/Base.xcconfig:4` is empty and `:5` pulls in the local file through `#include? "Local.xcconfig"` (ignored via `.gitignore:10`; `git ls-files Config` lists only `Base.xcconfig` and `Local.xcconfig.example`); after a CI checkout there is no `Local.xcconfig`, the team ID is empty, and CI explicitly disables signing (`.github/workflows/ci.yml:71-75`, iOS step `:209-212`).

More important is that **re-signing strips the entitlements**: every CI launch step runs `codesign --force --deep --sign - "$APP"` (ci.yml:83, :135, :156, :180). Measured on comparable local build products:

- `build/analysis-macos/Build/Products/Debug/XYZ.app`: `codesign -dv` → `Signature=adhoc, linker-signed`, `codesign -d --entitlements -` **prints nothing**;
- `build/analysis-macos-release/…/Release/XYZ.app`: likewise ad hoc, with no entitlements;
- by contrast `/Applications/XYZ.app` (the installed 0.5.27): carries `com.apple.security.app-sandbox=true`, `network.client`, `files.user-selected.read-write`, `files.bookmarks.app-scope`, the iCloud container and `get-task-allow`, signed by `Apple Development: Zhichao Li (T293LA2YX9)`.

The CI comment (ci.yml:132-134) says "unsigned CI build carries iCloud entitlements, ad-hoc sign without them so the process can start" — **the first half does not match reality**: a build with `CODE_SIGNING_ALLOWED=NO` embeds no entitlements (measured empty); the operation the second half describes does strip them, or never adds them. The net result: CI's gutter / launch / menu / acceptance runs all execute in a **non-sandboxed** process.

**Impact**:

- real sandbox-related defects (security-scoped bookmarks, container paths, the iCloud document scope, user-selected file permissions) can never be found by CI;
- the "user Mac / iCloud unverified" caveat that 0.5.28 repeats so often has a structural CI cause, not merely a missing environment;
- every launch step repeats a `--deep` re-sign (Apple explicitly discourages `--deep`), and the day the app really is signed with entitlements, this ad-hoc re-signing will fail or crash outright.

**Recommendation**: split CI into two lanes, "fast unsigned build" and "advisory signed build with a team"; the latter injects `DEVELOPMENT_TEAM` from a secret and launches the entitled app for a minimal smoke test; if signing is out of scope short term, at least state in README/CHANGELOG that "CI's UI evidence comes from a non-sandboxed process".

### 1.4 Hardened Runtime disabled: the release configuration cannot be notarized

`project.pbxproj:442` (Debug) and `:487` (Release) both set `ENABLE_HARDENED_RUNTIME = NO`. README:114 explains "off so that unsigned build can succeed" — but CI uses `CODE_SIGNING_ALLOWED=NO` and does not sign at all, so Hardened Runtime has nothing to do with "whether an unsigned build succeeds"; the explanation is misleading.

**Impact**: notarization (notarytool) for direct macOS distribution requires Hardened Runtime; as long as Release keeps it off, no notarizable product is possible. The installed version is signed with an Apple Development certificate (measured locally), not a Developer ID, and cannot be distributed externally.

**Recommendation**: enable Hardened Runtime for Release (Debug may keep it off); add `archive` + `notarytool` release scripts; fix the inaccurate causal claim in README.

### 1.5 Debug / Release differences

**Identical** (the two configurations match item by item, which means "switch behaviour per configuration" is barely used): `ENABLE_HARDENED_RUNTIME=NO` (`:442`/`:487`), `CODE_SIGN_ENTITLEMENTS` and its sdk conditions (`:437-440`/`:482-485`), `GENERATE_INFOPLIST_FILE=YES` (`:444`/`:489`), `INFOPLIST_FILE` and the macOS override (`:445-446`/`:490-491`), `PRODUCT_BUNDLE_IDENTIFIER=com.lizhichao.XYZ` (`:461`/`:506`), `SUPPORTED_PLATFORMS` (`:465`/`:510`), `SWIFT_VERSION=5.0` (`:471`/`:516`), `SWIFT_STRICT_CONCURRENCY=minimal` (`:470`/`:515`), `ENABLE_PREVIEWS=YES` (`:443`/`:488`).

**Different**: `DEBUG_INFORMATION_FORMAT` dwarf → dwarf-with-dsym (`:366`/`:415`); `GCC_OPTIMIZATION_LEVEL` 0 → s (`:372`/`:420`); `SWIFT_OPTIMIZATION_LEVEL` -Onone → -O (`:383`/`:426`); Release adds `SWIFT_COMPILATION_MODE=wholemodule` (`:425`) and `ENABLE_NS_ASSERTIONS=NO` (`:416`); Debug has `ENABLE_TESTABILITY=YES` (`:368`), `ONLY_ACTIVE_ARCH=YES` (`:380`) and `SWIFT_ACTIVE_COMPILATION_CONDITIONS=DEBUG` (`:382`). Measured, the Debug product is arm64-only and Release is universal (x86_64+arm64).

**Gaps**:

- CI builds **Debug only** (ci.yml:70, `:208`), so Release's wholemodule/`-O` path is never compiled in CI (the Lead's local build passes, but that is luck this time);
- there is no `SWIFT_TREAT_WARNINGS_AS_ERRORS` and no `GCC_TREAT_WARNINGS_AS_ERRORS`, so warnings never block;
- even on the Swift 6.4.2 toolchain the project stays in Swift 5 language mode with minimal concurrency checking: concurrency correctness is unguarded (see P2).

### 1.6 Consistency of the macOS / iOS targets with Info.plist and entitlements

**Structure**: a single `PBXNativeTarget` (`project.pbxproj:211-231`), `SDKROOT=auto` (`:464`/`:509`), `SUPPORTED_PLATFORMS = iphoneos iphonesimulator macosx` (`:465`/`:510`), switching the plist and entitlements through `[sdk=…]` conditions (`:437-440`, `:445-446`, `:482-485`, `:490-491`).

**The consistent parts** (measured products):

- The `NSUbiquitousContainers` container `iCloud.com.lizhichao.XYZ` appears in both `XYZ/Info.plist:55-66` and `XYZ/Info-macOS.plist:67-78`, and lines up with the entitlements' `icloud-container-identifiers` / `ubiquity-container-identifiers` / `icloud-services=CloudDocuments` (`XYZ/XYZ-macOS.entitlements:13-24`, `XYZ/XYZ-iOS.entitlements:5-16`); both bundled macOS and iOS products contain the key.
- macOS-only capabilities live only in the mac entitlements: App Sandbox (`:5-6`), `network.client` (`:7-8`; README:16 explains that iOS does not add this key, which matches WKWebView's default behaviour in the iOS sandbox), user-selected read-write (`:9-10`) and app-scope bookmarks (`:11-12`); the iOS entitlements keep only iCloud (`:5-16`) and do not pile on sandbox or network keys.
- `CFBundleDocumentTypes`: both plists declare Markdown + plain text (`XYZ/Info.plist:5-31`, `XYZ/Info-macOS.plist:5-30`), and macOS additionally declares folder (`XYZ/Info-macOS.plist:31-43`), consistent with the product positioning of a Mac folder workspace and an iOS document browser; `UTImportedTypeDeclarations` is identical in both.
- `LSMinimumSystemVersion` is absent from the hand-written plists but is generated from `MACOSX_DEPLOYMENT_TARGET=14.0` (`project.pbxproj:378`/`:422`), and the macOS product measures `14.0`; the iOS product has no such key (correct).
- The bundled iOS product: `CFBundleShortVersionString=0.5.28`, `UISupportsDocumentBrowser=true`, `LSSupportsOpeningDocumentsInPlace=true`, `NSUbiquitousContainers` present, `zh-Hans.lproj`/`en.lproj` present.

**Inconsistencies / redundancy**:

- Every `INFOPLIST_KEY_*` takes effect unconditionally (`:447-455`, `:492-500`), so **the measured macOS product's Info.plist carries iOS-only keys**: `UILaunchScreen`, `UIStatusBarStyle`, `UISupportedInterfaceOrientations`, `UISupportsDocumentBrowser`, `UIApplicationSupportsIndirectInputEvents`. For a macOS app this has no functional effect, but it shows the configuration was never narrowed per platform, and it will raise meaningless warnings once App Store validation/review enters the picture.
- The container ID and bundle ID are hard-coded in many places (pbxproj:461/506, both plists, both entitlements, CLI line 6, `Scripts/xyz-test.sh:31`, and so on), with no single constant and no CI consistency check (see P2-5).

## 2. Per-step assessment of CI

Workflow: `.github/workflows/ci.yml` (212 lines), triggered by `push` (all branches) + `pull_request` (`:3-5`), with `concurrency.group` keyed by ref and `cancel-in-progress: true` (`:7-9`), `permissions: contents: read` (`:11-12`), and a single job `build` on `macos-latest` (`:15-16`).

### 2.1 "Select newest Xcode" (`:20-52`)

- Approach: Python scans `/Applications/Xcode*.app`, reads `CFBundleShortVersionString`, sorts them as numeric tuples, takes the newest, writes `/tmp/xyz-xcode-path`, runs `sudo xcode-select -s`, writes `DEVELOPER_DIR` into `$GITHUB_ENV`, and prints the version.
- **Fragility**: `macos-latest` is a moving target (the runner image and preinstalled Xcode change); "always take the newest" means the same commit may compile with a different Xcode on a different date, so historical green runs are not reproducible. The cloud run recorded in CHANGELOG:25 was "Xcode 26.6, MacOSX 26.5 SDK" while this machine has Xcode 27.2 — the same commit is not equivalent across the two toolchains.
- Using both `sudo xcode-select -s` and `DEVELOPER_DIR` (`:49-50`) is redundant; the fixed path `/tmp/xyz-xcode-path` can be pre-seeded on a shared runner (low risk); the SDK/simulator runtime is not pinned.
- **Recommendation**: pin an Xcode version range in the project docs (or an `XCODE_VERSION` env var), and change CI to "find the specified version and fail explicitly if it is absent", so the toolchain never changes silently.

### 2.2 "Test xyz command" (`:54-55`) → see §5; 6/6 passes, but it only tests dry-run output.

### 2.3 "Test XYZCore" (`:57-59`)

- `swift test --package-path XYZCore`: it covers only the local Swift package (the Lead measured 191 tests / 0 failures). **The app target has no XCTest target at all** (the pbxproj has 1 native target; the scheme's `TestAction` is empty, `XYZ.xcodeproj/xcshareddata/xcschemes/XYZ.xcscheme:25-30`), so the ~20k lines of app code in WorkspaceSession/WorkspaceView/EditorChrome and friends have no unit tests to run.
- There is no `--enable-code-coverage`, no upload of test results/`xcresult`, and no caching: every run re-fetches `swift-markdown`/`swift-cmark` (Package.resolved pins the revision, but the network is an extra failure source).

### 2.4 "Build macOS" (`:61-75`)

`xcodebuild -project … -scheme XYZ -destination 'platform=macOS' -configuration Debug -derivedDataPath build/macos CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=- build`.

- Debug only and unsigned only; `CODE_SIGN_IDENTITY=-` together with `CODE_SIGNING_ALLOWED=NO` is self-contradictory (the latter already neutralizes the former) and merely spells the "ad-hoc" intent out on the command line;
- it only builds: there is no `xcodebuild analyze`/`-enableAddressSanitizer`/Release compile anywhere.

### 2.5 "Check Editing line numbers" (`:77-101`)

- Find the product → `codesign --force --deep --sign -` (`:83`, which strips entitlements, see §1.3) → set `XYZWindowShots` and then execute `XYZ.app/Contents/MacOS/XYZ -XYZCheckGutter -ApplePersistenceIgnoreState YES` directly (`:87`, no `open`, no sandbox) → poll 90 times × 1 second, kill and `exit 1` on timeout (`:90-101`).
- The `-XYZCheckGutter` implementation (`XYZ/Editor/GutterSnapshot.swift:9-50`) runs the whole self-check synchronously inside `applicationDidFinishLaunching` and then `exit(0/1)` (the hook is at `XYZ/Workspace/WorkspaceWindowController.swift:602`): off-screen rendering with TextKit 1/2 pixel counting, composited-layer screenshots, window-level `CGWindowListCreateImage` + Vision OCR, file read-back, sidebar fit, and 8 UI acceptance cases.
- **Weak points**:
  1. **A hard 90-second budget** covers all of the above (including multiple screenshots + OCR + 8 cases, each with its own `waitUntil(4)`/`waitUntil(6)`); on a slow runner this goes red spuriously. The CI history of 172/380 failures and only 10 successes in the last 100 runs is consistent with such a heavy gate (API-verified).
  2. **Window screenshots depend on a deprecated API**: `CGWindowListCreateImage` (`GutterSnapshot.swift:1031`, deprecated since macOS 15) needs the Screen Recording TCC permission; when unavailable it falls back to `compositedImage` (`:1063`, which renders the layer rather than the WindowServer picture). The code uses a "capture control" self-check to tell a blind capture apart (`:458-500`, `:486-497`) — a genuine strength, but it also means CI green/red is governed by the runner's TCC/WindowServer behaviour.
  3. **Window screenshots cannot see the WKWebView**: the code admits this itself (`GutterSnapshot.swift:659` prints "window picture does not include web views"), and CHANGELOG:48 states the same ("window capture does not show web-view pixels"). In other words, Reading (Markdown rendering), the product's main interface, **has never been validated by window screenshots**.
  4. On failure it only `cat`s the log, and the log files (`gutter.log`/`launch.log`/`menu*.log`) are **not uploaded as artifacts**; the only artifact is the screenshot directory (`:117-123`), whose diagnostic value is limited.

### 2.6 "Check original UI acceptance" (`:103-115`)

- It reads the same `gutter.log` and passes only when `grep -q 'ACCEPTANCE_OK'` succeeds; otherwise it greps the `ACCEPTANCE` lines and `exit 1`s.
- In implementation this is an **honest split**: the body result (`GUTTER_OK`/`GUTTER_MISSING`, `GutterSnapshot.swift:41-48`) is separate from the UI acceptance result (`:1604-1631`, 8 cases, printing `ACCEPTANCE_OK` only when all pass, otherwise `ACCEPTANCE_FAIL N`); CHANGELOG:32 states explicitly that "the body result and the UI acceptance result are separate".
- **Problems**:
  1. **HEAD is currently red here**: CHANGELOG:40 records 5 failing cases on `da9730d` (nested-file / collapse-header / dividers / mode-labels / empty-line-prefs, `ACCEPTANCE_FAIL 5`), while `da9730d..HEAD` makes **zero changes** to `XYZ/Editor/GutterSnapshot.swift` (`git log --oneline da9730d..HEAD -- XYZ/Editor/GutterSnapshot.swift` is empty) — HEAD only adds documentation and deletes XCUI commits. The API-verified HEAD run `42332912178` fails at exactly this step.
  2. **A failure buries the later checks**: after an acceptance failure, the Launch/Menu steps guarded by `if: steps.macos.conclusion == 'success'` are skipped (as in the API-verified run), so only one stage of problems is exposed per run, making the fix-and-rerun loop extremely long (172 failures, 71 cancellations).
  3. **The verdict is a grep**, not a structured report; the `ACCEPTANCE_FAIL` count and the failing items exist only in the log, with no JUnit and no summary.
  4. **"Pass" means little**: these cases drive synthesised fixture windows inside the same process via `trackingClick`/event injection (`GutterSnapshot.swift:1618-1625` and the individual `accept*` functions), not real user input; the XCUI path was tried and abandoned (`4785e4c` added an `XYZUISmoke` target, `84d4d5d` deleted it again; CHANGELOG:25 records `Runningboard error 5 / Launchd job spawn failed` on the runner, with the app never launching). So **no real click-through or UI automation validation exists**.

### 2.7 "Upload editor window shots" (`:117-123`)

`if: always()` + `actions/upload-artifact@v4`, path `build/macos/shots`, `if-no-files-found: ignore`. Uploading on failure is a strength, but only screenshots are uploaded, not logs; and artifacts expire after the default 90 days, so the many "cloud window pictures" pieces of evidence in CHANGELOG will vanish over time (see P1-9).

### 2.8 Launch / Menu / Chinese Menu (`:125-198`)

- Launch (`:125-148`): re-sign → run the binary directly → **only check that it has not exited within 8 seconds**, then `kill`. A hung app, a missing window or a white screen all count as "pass".
- Open Folder menu (`:150-172`): `-XYZCheckFileMenu` (`XYZ/Workspace/FolderOpening.swift:499-527`), which checks that the localized "Open Folder…" item exists in the File menu, that the shortcut is ⌘⇧O, that the target is correct, and `openPanelHooked`/`openDocumentHooked` (`:519-525`) → prints `FILEMENU_OK` as the exit code. The scope is limited to the menu item and the hooks; it does not verify that the open panel can actually pick a directory.
- Chinese menu (`:174-198`): adds `-AppleLanguages '(zh-Hans)'`, first runs `test -d "$APP/Contents/Resources/zh-Hans.lproj"` (`:181`), then **greps exactly one Chinese menu title** ("Open Folder…", `:190`). The catalog happens to contain that string, so the check is a tautology; the other 47 missing translations (§4) cannot be detected at all.

### 2.9 "Build iOS Simulator" (`:200-212`)

- `-destination 'generic/platform=iOS Simulator'`, Debug, unsigned, compile only. No booted simulator, no iOS XCTest/XCUI, no `-derivedDataPath` (products land in the default DerivedData and are not retained), and no entitlements validation.
- It shares the same target/version/plist merging logic as macOS, so an iOS compile passing only means "it compiles".

### 2.10 Structural CI gaps

- No caching (SPM / DerivedData): every run re-fetches dependencies and compiles from scratch;
- no `timeout-minutes` (the job default is 6 hours; one hang can burn the whole allowance);
- dual triggers `push` (all branches) + `pull_request` (`:3-5`), while `concurrency` is grouped by ref, so **push runs and PR runs do not cancel each other** and the same commit runs twice (CHANGELOG cites push runs and PR runs separately too, e.g. line 38); no `paths-ignore`;
- the build steps use `if: ${{ !cancelled() }}` (`:63`, `:201`), so even after `swift test` has failed, the full macOS/iOS builds and UI checks still run (wasteful, though arguably a deliberate attempt to gather more failure information);
- no lint/format step (this machine has swiftlint 0.65.1 / swiftformat 0.64.6 installed, the repo has no configuration; the Lead ran the default rules and got 468 findings for the app and 138 for core, mostly style — debt exists but there is no gate);
- no plist lint, no pbxproj/disk consistency check, no version consistency check, no Release build, and no archive/notarize/tag/release job;
- no job matrix and no `xcodebuild test` (because there is no test target).

### 2.11 Degree of local reproducibility

- `sh Scripts/xyz-test.sh` is locally reproducible (measured 6/6 ok); `swift test --package-path XYZCore` is reproducible (Lead: 191/0); README:84-106 gives the unsigned build commands for macOS/iOS, and the Lead measured Debug/Release/iOS Simulator all BUILD SUCCEEDED (with a single run-script warning).
- **The UI checks are not reproducible on demand**: no README or developer document explains how to run `-XYZCheckGutter`/`-XYZCheckFileMenu` locally (`grep` finds them only in CHANGELOG and ci.yml); results depend on WindowServer/TCC/Vision and the macOS version, so a local run and a cloud-runner run are not equivalent.
- `Config/Local.xcconfig` exists on this machine (`DEVELOPMENT_TEAM = Z4FMG2KTPM`, ignored), so local Xcode can sign; a clean clone cannot.

### 2.12 What each "pass" does not prove about the product (explicit list)

| CI signal | What it actually proves | What it does not prove |

### 5.1 `XYZ/Resources/bin/xyz` (137 lines, shipped inside the app at `Contents/Resources/bin/xyz`)

Behaviour: `resolve_self` resolves symlinks (`:8-19`) → derive the app path (`:21-22`) → `-h/-V/-n/--` parsing (`:72-90`) → path normalization (`:50-70`) → hand-off through a `/tmp` temporary file (`:92-117`) → `open -b com.lizhichao.XYZ` (`:119-137`), with `XYZ_CLI_DRY_RUN=1` printing only and not executing (`:124-131`).

Measured (the CLI in the repo and the CLI of the installed app):

- `xyz --version`: the installed version prints `0.5.27` (read from `Contents/Info.plist`'s `CFBundleShortVersionString`, `:41-48`); invoked through a `/tmp` symlink it also prints `0.5.27` → `resolve_self` works.
- `xyz -z`: `unknown option`, exit 2 ✅; `xyz -- -n`: treated as a path, reports `No such file`, exit 1 ✅; `sh Scripts/xyz-test.sh` 6/6 ok ✅.

**Bug (P1): the documented `~` / `~/...` paths are broken.** POSIX specifies that `case` patterns undergo tilde expansion, so the `~)` and `~/*)` patterns on `:53` and `:54` become `$HOME` / `$HOME/*` at runtime and can never match a literal `~`; the argument falls through to the `*)` branch on `:56` and is concatenated into `$PWD/~...`, which then errors. Measured:

```
$ XYZ_CLI_DRY_RUN=1 XYZ/Resources/bin/xyz '~'
xyz: ~: No such file or directory   (exit 1)
$ XYZ_CLI_DRY_RUN=1 XYZ/Resources/bin/xyz '~/Notes'
xyz: ~/Notes: No such file or directory
```

Yet the CLI's own `--help` says on line 30 "Open a folder." for `xyz ~/Notes`, and README:28 likewise teaches users `xyz ~/Notes`. `Scripts/xyz-test.sh` does not cover `~`, spaces, `--`, `-V`, unknown options or symlinks (`:27-48` tests only help/./relative file/-n/missing/bare).

**Other problems**:

- Predictable temporary files `/tmp/xyz-cli-paths.$$`, `/tmp/xyz-cli-fail.$$` (`:98`, `:102-105`, `:116-117`): a symlink/pre-seeded-file attack surface on shared `/tmp`, plus concurrent collisions; use `mktemp -d` + `trap`.
- `xyz ""` (an empty argument) is silently dropped (`:95-96` skips empty lines), behaving like plain `xyz`, which is counter-intuitive if you expect "open the current directory".
- `resolve_self`'s `while [ -L "$target" ]` (`:10-17`) has no hop limit, so a symlink loop spins forever.
- The bundle ID is hard-coded (`:6`), duplicating pbxproj:461/506 with no consistency check; after a bundle ID change the CLI silently stops working.
- In `exec open $flags "$@"` (`:137`) `$flags` is unquoted (shellcheck SC2086), safe only because the arguments are controllable; `resolved=""` (`:92`) is an unused variable (shellcheck SC2034).

### 5.2 `Scripts/xyz-test.sh` (50 lines)

- Coverage: the first line of `--help`, `.`, a relative file, multiple paths with `-n`, the missing-path error, and no arguments (`:27-48`); it cleans up with `mktemp -d` + `trap` (`:22-23`). Measured locally: 6/6 ok; CI runs it every time (`ci.yml:54-55`).

The expected values are hand-written too, so when the bundle ID or the output format changes, the test changes alongside the CLI and cannot detect that the two disagree.

### 5.3 `tools/make_icons.py` (195 lines)

- Dependencies: `fontTools` is imported at **module top level** (`:26-31`), with no `requirements.txt`/venv pin; fontTools is not installed on this machine → `python3 tools/make_icons.py --help` fails outright with `ModuleNotFoundError: No module named 'fontTools'` (measured). ## 7. Findings (by severity)

### P0 — Build/release/security/integrity risks

**P0-1 No publishable build at all: no tags, no release/notarization pipeline, Hardened Runtime off in Release, and the installed version signed with a development certificate**
- Evidence: `git tag` is empty; `.github/workflows/` holds only `ci.yml` (no release job); `project.pbxproj:487` (Release `ENABLE_HARDENED_RUNTIME = NO`); `codesign -dv` on the local `/Applications/XYZ.app` = `Authority=Apple Development: Zhichao Li (T293LA2YX9)` (not a Developer ID); the README:114 rationale has nothing to do with `CODE_SIGNING_ALLOWED=NO`.
- Impact: 0.5.28 cannot become a distributable product; notarization is impossible; users cannot install it under Gatekeeper; "rollback/candidate release" exists only on the developer machine.
- Recommendation: enable Hardened Runtime for Release; add an `archive` + `notarytool` release job (Developer ID certificate/key via secrets); bind the tag to the build number; correct the Hardened Runtime explanation in README.

**P0-2 CI validates a binary different from the app users run: unsigned build + ad-hoc re-sign strips the entitlements, so CI never tests the sandbox/iCloud/bookmarks**
- Evidence: `ci.yml:71-75` (`CODE_SIGNING_ALLOWED=NO`), `:83`/`:135`/`:156`/`:180` (`codesign --force --deep --sign -`); a comparable local build product has empty `codesign -d --entitlements -` and `Signature=adhoc, linker-signed`; the installed 0.5.27 carries `app-sandbox`/iCloud/bookmarks (measured); the `ci.yml:132-134` comment wrongly claims the unsigned build carries iCloud entitlements.
- Impact: zero coverage of security-scoped bookmarks, container paths, iCloud documents, user-selected file permissions, WKWebView inside the sandbox and other real paths; CI green says nothing about "it runs inside the sandbox".
- Recommendation: add an advisory signed job with a team (injected from secrets) that runs a minimal launch/file-IO/bookmark smoke test; at the very least write "CI has no sandbox" into README/CHANGELOG so it is not misread.

**P0-3 0.5.28/44 is red on its own CI, and the same version number covers two different trees (no tag to disambiguate)**
- Evidence: API-verified HEAD run `42332912178` fails at `Check original UI acceptance`; `CHANGELOG.md:40` records `ACCEPTANCE_FAIL 5`; `git log --oneline da9730d..HEAD -- XYZ/Editor/GutterSnapshot.swift` is empty (the failing cases were not fixed); `git rev-list --count 02dac3c..HEAD` = 18, and all 18 commits are 0.5.28/44 (`git show 02dac3c:Config/Base.xcconfig` equals `HEAD:`); `git tag` is empty.
- Impact: anyone outside who checks out/tags 0.5.28 per the docs may get a tree that never passed acceptance; "the 0.5.28 that passed CI" cannot be reproduced.
- Recommendation: first freeze a commit and tag `v0.5.28` when acceptance is fully green; do not call a candidate releasable before the failing cases are fixed; record "current gate version + green commit" in CHANGELOG.

### P1 — High maintenance cost / CI false positives and false negatives

**P1-1 Hand-written pbxproj (no project.yml/xcodegen) → new files are registered by hand, and a missed registration silently omits compilation**
- Evidence: no `project.yml` (`find`/`ls` find nothing; xcodegen 2.46.0 installed but unused); no generator marker in the pbxproj; UUIDs are synthetic sequential `8A/8B/8C0…` (`project.pbxproj:10`, `:46`); 39 hand-written `PBXFileReference` entries and 27 sources entries, currently 27/27 consistent with disk (script comparison).
- Impact: high maintenance cost and error-prone; CI performs no disk↔pbxproj consistency check.
- Recommendation: migrate to xcodegen (commit `project.yml`) or add a consistency-check script to CI.

**P1-2 The CI gate is slow, red and floating: 380 runs with only 137 successes, only 10 successes in the last 100 runs, and failures skip the later steps**
- Evidence: API-verified statistics (137/172/71; 10 successes in the last 100 runs; 11-06 alone had 16/101/22); `ci.yml:20-52` "select the newest Xcode" + `macos-latest`; `ci.yml:90-101` 90-second hard timeout; after an acceptance failure the launch/menu steps guarded by `if: steps.macos.conclusion == 'success'` are skipped (API-verified 42332912178).
- Impact: long feedback cycles and only one stage of problems exposed per run; historical green runs are not reproducible (the CHANGELOG:25 run was on Xcode 26.6, this machine has 27.2).
- Recommendation: pin the Xcode version; give each step `timeout-minutes`; on failure run the information-gathering steps with `always()`; split acceptance into its own job with a structured failure list.

**P1-3 2,459 lines of self-check code ship in the release bundle (no `#if DEBUG`), acting as the "test framework" without living in a test target**
- Evidence: `XYZ/Editor/GutterSnapshot.swift:9-50` (the full `-XYZCheckGutter` self-check); the hook is compiled unconditionally at `XYZ/Workspace/WorkspaceWindowController.swift:602` (and the `FileMenuCheck` at `:625`); the pbxproj has 1 target and the scheme's `TestAction` is empty (`XYZ.xcscheme:25-30`).
- Impact: the release binary contains Vision/screenshot/file-read-back code; test logic is coupled to product logic (changing product code forces keeping the self-check working); the app layer cannot be unit-tested with XCTest.
- Recommendation: move the self-check into a separate UI test target (or at least wrap it in `#if DEBUG`); add XCTest coverage for pure logic such as WorkspaceSession/WorkspaceFilePolicy.

**P1-4 The bilingual promise fails for at least 47 user-visible strings, and CI checks only one menu title**
- Evidence: the item-by-item `file:line` list in §4.2 (menus `XYZ/XYZApp.swift:107/112/117/141/144/151`; context menu `EditorChrome.swift:606-612`; search panel `GlobalSearchPanel.swift:62/226/241-243/374-377/527-529`; sidebar `WorkspaceSidebar.swift:824/1082-1083/1122`; settings `SettingsView.swift:50/56/132`); catalog 234 keys/232 zh (measured); the catalog's last change is `bfc33f7` (11-03); CI's Chinese-Open-Folder grep (`ci.yml:190`) happens to hit an already-translated item.

**P1-5 The CLI `xyz` advertises `~` / `~/...` paths in its help text but they do not work**
- Evidence: `XYZ/Resources/bin/xyz:53-54` (the `~)`/`~/*)` patterns); `:30` (the usage example `xyz ~/Notes`); README:28; under POSIX, `case` patterns undergo tilde expansion (measured `sh -c 'case "~" in ~) …'` = NOMATCH); measured `XYZ_CLI_DRY_RUN=1 xyz '~'` and `xyz '~/…'` both exit 1 with `No such file or directory`; `Scripts/xyz-test.sh:27-48` does not cover it.
- Impact: a feature README/help teaches users errors straight away; user shell scripts will fail.
- Recommendation: switch to `case $input in "~"|"~/"*) …` or test for the `$HOME` prefix first; add tests (`~`, `~/x`, spaces, `--`, `-V`, unknown options, symlinks).

**P1-6 Release/version records rely on volatile cloud evidence: CHANGELOG run URLs + 90-day artifacts cannot be re-verified long term**
- Evidence: `CHANGELOG.md:17/25/38/40` (GitHub Actions run URLs); `ci.yml:117-123` (only screenshots are uploaded, not logs); screenshots/logs exist only in artifacts (90 days by default).
- Impact: the "where was this verified" part of the version record becomes inaccessible months later; third parties cannot audit.
- Recommendation: commit each run's commit, Xcode/macOS versions, key log summaries (the `GUTTER_OK`/`ACCEPTANCE_FAIL` lines) and screenshot hashes into the repo; or use long-lived release assets.

**P1-7 No app test target, no Release build, no lint gate: CI only proves "Debug compiles + the self-checker runs"**
- Evidence: the pbxproj has a single target; the scheme's `TestAction` is empty (`XYZ.xcscheme:25-30`); `ci.yml:61-75` builds Debug only and `:200-212` only compiles iOS; there is no lint step (`grep lint ci.yml` is empty); swiftlint/swiftformat are installed locally but the repo has no configuration (`find` finds no `.swiftlint*`/`.swiftformat`); the Lead's default-rule counts are 468 app / 138 core.

**P1-8 The xyz CLI uses predictable `/tmp` temporary files (symlink/concurrency risk)**
- Evidence: `XYZ/Resources/bin/xyz:98` (`/tmp/xyz-cli-fail.$$`), `:102` (`/tmp/xyz-cli-paths.$$`), `:103-105`, `:116-117`.
- Impact: on shared `/tmp` a pre-seeded symlink can point at any writable file (truncation/write), and concurrent invocations overwrite each other; a local security-hygiene issue.

**P1-9 The risk of recording before verifying: the version record admits failures, and the "passed" evidence form (window OCR screenshots) cannot see the main Reading UI**

**P1-10 The icon generation script is not reproducible and its dependencies are undeclared**
